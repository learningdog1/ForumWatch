# ForumWatch 功能分区与交互骨架（ia-interaction）

> 定位：**五个界面设计的共同骨架**。后续每张界面设计（监控台 / 去向 / 历史命中 / 日报 / 设置）必须遵守本文的分区职责、命名定稿与交互模式；界面设计可以细化表现，不得推翻分区边界。
> 输入材料：`design/redesign/audit.md`（下称 audit）、`design/redesign/product-context.md`（下称 pc）、`design-system/forumwatch/MASTER.md`、`design/redesign/design-system-notes.md`（下称 dsn）。
> 佐证检索：ui-ux-pro-max 技能，`search.py` 共跑 3 次（命令与命中见附录 A）；另按 SKILL.md 指引按需读取 `references/quick-reference.md` 相应条目（属读文件、不计入检索次数）。

## 0. 六条设计原则（全部决定由它们推导）

1. **看 / 改分离**：界面一半是"看数据"（监控台 / 去向 / 历史命中 / 日报），一半是"改配置"（设置）。侧栏只用一条分隔线做这个切割，不在查看区内部再分组（5 项平级是导航舒适区，检索佐证见 A-1：面包屑「不用于扁平单级站点」）。
2. **可解释性前置**（pc §3.3：差异化卖点）：「为什么没推送」必须是侧栏上一眼可懂的名字与最短的排障路径，而不是空态里的一句提示（audit §2 对现状的批评）。
3. **draft 单源**：设置的一切修改走 draft → 保存生效（pc §6.3），一个 dirty 状态、一个保存栏、一份守卫。子导航是锚点不是路由，就是为了不拆散这个单一数据源。
4. **错误是一等公民**（audit 问题 #1；dsn §7 红线「禁隐藏错误状态」）：所有数据面「失败 ≠ 空」，统一错误条 + 重试 + 旧数据保留（范本：audit §4.3 统计面板）。
5. **活列表阅读优先于新鲜度**（dsn §2 telemetry 规则②：轮询类 UI 必须提供暂停/频率控制）：用户正在读列表时，自动插入/自动刷新必须让位，用「N 条新」角标承接（范本：LogView 跟随暂停，audit §5.7.2）。
6. **键盘优先**（dsn §6：桌面监控用户重键盘）：导航、保存、列表移动都要有快捷键；焦点环常显。

## 1. 导航结构（定稿）

### 1.1 分区图

```
┌ 侧栏（primary nav，现有位置与 184px 量级保留）
│
│  ● 监控台          现在：运行状态 + 最近命中 + 日志（活页，事件驱动）
│  ● 去向            为什么没推送：实时环 + 7 天落盘，14 类判定结果
│  ● 历史命中        全量命中记录 + 统计画像（永久数据，手动刷新）
│  ● 日报            每日 AI 总结（14 天 + 更早可达）
│  ─────────────     （唯一一条分隔线：查看区 / 设置区）
│  ⚙ 设置            ── 全部配置，draft-保存模型
│       └ 子导航（secondary，锚点滚动，非路由）：
│          ① 监控内容    来源 · 关键词 · 价格规则
│          ② 智能匹配    监控模式 · AI 模型 · 相似降噪
│          ③ 推送通知    通道 · 策略 · 路由规则 · Telegram 遥控
│          ④ 运行与通用  轮询 · 每日总结 · 网络(代理) · 开机自启
│          ⑤ 数据与诊断  数据备份 · 匹配测试台
│          ⑥ 关于        版本 · 更新检查
│
└ 底部迷你运行状态（保留——托盘常驻身份的界面暗示，pc §6.1）
```

### 1.2 命名决定（逐项给理由）

| 现名 | 定稿 | 决定与理由 | 放弃了什么 |
|---|---|---|---|
| 监控台 | **监控台** | 保留。「现在正在发生什么」的价值已清楚（audit §2），且是默认落地页 | — |
| 流水 | **去向** | 改名。audit §2/§7.3：会计隐喻不传达价值，页内叫「处置流水」、价值写在空态。新名回答用户真实问题——"这条帖子去哪了/为什么没推送"。页内大标题「处置去向」，副题「每条帖子的判定结果 · 为什么没推送，在这里查」 | 「处置」（更技术化，新用户理解成本高）、「追踪」（语义泛） |
| 今日回顾 | **日报** | 改名。audit §2：页面实际可看任意历史日期，名不符实；且 tab 名与页内名「日报」两套并存。对齐页内名，页内副题「AI 每天生成的命中总结 · 可回看历史日期」 | 「每日总结」（与设置卡同名，混淆页面与配置）、「回顾」（太泛） |
| 历史命中 | **历史命中** | 保留。audit 只点名两个名字有问题；改名有迁移成本，此名可懂 | 「命中记录」（无增益） |
| 设置 | **设置** | 保留 | — |

### 1.3 重排决定：顺序 = 数据新鲜度谱系

现状顺序 监控台 / 今日回顾 / 历史命中 / 流水 / 设置 → 定稿 **监控台 / 去向 / 历史命中 / 日报 / 设置**。

理由：
1. **新鲜度递减与 pc §6.2 的三档数据新鲜度同构**：事件驱动（监控台）→ 定时轮询（去向，10s 自刷）→ 手动刷新（历史命中）→ 每日快照（日报）。侧栏自上而下就是"离现在多远"。
2. **排障路径最短**：监控台回答"发生了什么"，去向回答"为什么这条没推送"——两者是同一条数据的两个视角，紧邻放置使最高频跨页跳转（audit §4.1-§4.4 反复出现的排查动线）变成一跳。
3. 日报是"总结的总结"，回顾组末位，低频浏览靠位置暗示。

放弃了什么：**保守方案（只改名不重排）**。三个 tab 换位对老用户有一周级适应成本，但换来侧栏顺序与心智模型（新鲜度 × 排障动线）一致，值得；五项平级结构本身不动，重排不是结构变更。

### 1.4 结构决定：不分组、不合并、不加层级

- **不加组标题**：5 项远未超载（quick-reference `bottom-nav-limit`：主导航 ≤5；检索 A-1：面包屑「不用于扁平单级站点」）。加组标题是过度结构化，违背 variance 3 的可预测性（dsn §1）。
- **不合并「去向」与「历史命中」**：虽然都是"记录"，但任务不同（查解释 vs 查记录）、数据形态不同（内存环实时 + 7 天 vs 永久落盘分页）、刷新档位不同（pc §6.2）。合并会把两种查询语义塞进一页。
- **不把设置拆成多个顶层 tab**：拆了侧栏就超 5 项，且「设置 = 改配置」的单一心智被稀释，dirty 守卫要跨页追踪。
- **层级**：侧栏是 primary，设置内子导航是 secondary，视觉弱一档（更小字号/更小图标）——quick-reference `nav-hierarchy`（MD：primary 与 secondary 必须清晰分离）。
- **快捷键**：`Cmd/Ctrl+1..5` 切换分区（audit §5.4：现状零快捷键）；侧栏 active 项补 `aria-current`（同上）。
- 保留资产：dirty 时「设置」项的未保存圆点、底部迷你运行状态与托盘 tooltip 同口径（audit §5.7.4；pc §6.1）。

## 2. 设置页信息架构（重灾区治理）

### 2.1 十七卡 → 六组（完整映射，无遗漏）

| 子导航组 | 收纳的卡（=现状卡名） | 组职责（一句话） | 相对现状的变化 |
|---|---|---|---|
| ① 监控内容 | 来源、关键词、价格规则 | 定义"监控什么、什么算命中"的判定输入 | 价格规则从第 7 位前移；组序即配置依赖序 |
| ② 智能匹配 | 监控模式、AI 模型、相似降噪 | 定义三种命中方式中 AI 与降噪的判定参数 | 三张散卡归拢；匹配测试台**移出**此区间 |
| ③ 推送通知 | 推送通道、推送策略、路由规则、Telegram 遥控 | 定义"推给谁、何时推、走哪条路" | 「行为」卡的推送总开关（临时静音）并入推送策略 |
| ④ 运行与通用 | 轮询、每日总结、网络(代理)、开机自启 | 定义应用自身的运行节奏与系统行为 | 「行为」卡拆解：自启归此；总开关归③；卡名「行为」废止（audit §5.1：名字不指向内容） |
| ⑤ 数据与诊断 | 数据（备份）、匹配测试台 | 只读诊断与数据迁移，非配置 | 匹配测试台从配置流中段（audit §2：插在价格规则与 AI 模型之间打断配置流）移到页尾独立组 |
| ⑥ 关于 | 关于 | 版本与更新 | 独立底部，惯例位置 |

分组依据是**用户任务**（改什么 → 在哪组）而非实现模块；组名全部用任务语言。佐证：quick-reference `field-grouping`（MD：相关字段逻辑分组）。

### 2.2 子导航形式：设置页内左侧锚点栏（非路由）

设置页主区劈出约 160px 二级栏：6 个锚点项，点击滚动到位，滚动联动高亮。

理由：
1. **保住 draft 单源**：单页滚动 + 锚点 = 一份数据面、一个 dirty 状态、一个保存栏、一条 leavebar 守卫。改成路由式子页（或顶层多 tab）要把 draft/dirty/保存栏复制或提升到每页，复杂度暴涨，且现有守卫资产（audit §5.7.4）全部要重做。
2. **修正现状最高频痛点**：audit 问题 #2——在第一张卡改一个词要滚过 16 张卡才能保存。锚点栏 + 吸底保存栏后，任何组内修改到「保存」的距离 ≤ 一屏。
3. **层级清晰**：primary（侧栏，切换数据面）/ secondary（锚点，同数据面内定位）两档视觉区分（quick-reference `nav-hierarchy`）。
4. **支持跨页深链**：历史命中的零命中关键词可以一键跳「设置 → 监控内容 → 关键词卡」（见 §4 流 C）——锚点天然支持带目标定位。

放弃了什么：**顶部横向 chips**（省了宽度但 6 组横排拥挤、且与卡片流的视觉关联弱）；**手风琴全折叠**（可见性损失：折叠态下"哪里有什么"不可发现，17 卡的内容用户需要扫视定位）。

### 2.3 渐进披露（三级）

- **L0 导航级**：子导航 6 组自选入口——代替现状"滚动扫描 17 卡"的定位方式。这是第一层披露：用户先选任务组，只见该组卡片流。
- **L1 组级**：组内卡片**默认平铺可见，不做组内折叠**。理由：设置是低频但目标明确的任务面，折叠藏起的配置等于不存在的配置（可发现性 > 视觉整洁）。唯一例外（可选 P2，不进首版骨架）：首启空配置时显示「快速上手」引导卡（关键词 + 通道两步），对应 pc §4.1 七步上手的第 2/4 步。
- **L2 卡级**：**实体行编辑默认收起为摘要行**——来源行、通道行、价格规则行现状已有「编辑」展开（pc §5.3），统一推广到路由规则（现状只有删除不可编辑，audit §4.5 问题 4），并给路由规则上下移按钮（顺序=优先级，现状要"删除重加"，audit 问题 #8）。per-source 过滤维持"一次只展开一行"。
- **L3 行级**：hint 常显小字（现状 Field hint 行模式保留）；高级参数（AI 自定义 Base URL、代理作用域细节）收进「高级」折叠行。

配套结构修正（属于骨架级，界面设计必须执行）：
- **废除 `.card-scroll` 嵌套滚动**（audit §4.5 问题 5：卡内 280px 滚动套在整页滚动里）：卡内列表取自然高度，由设置页整体滚动承担；超长列表（如 20 条路由）给「展开全部 N 条」而非内嵌滚动。
- 小卡合并颗粒度：轮询 / 每日总结 / 自启等 1-2 控件项归入④组后按行排布，不再各自成"卡"，消除 audit §2 批评的颗粒度不齐。

### 2.4 保存栏（吸底）与「放弃修改」

- 保存栏 **sticky 吸底**，常驻可见：`保存设置`（primary）+ `放弃修改`（次级，danger 描边）+ 状态文案区。快捷键 `Cmd/Ctrl+S`（audit 问题 #2 三缺口一次补齐）。
- 状态文案生命周期规则（修 audit 问题 #7）：dirty 一旦为真，立即清除「已保存·时刻」旧文案，替换为「有 N 处未保存修改」；保存成功才显示「已保存 · HH:MM:SS（部分值已按规则修正…）」。两者互斥，不允许并存误导。
- 「放弃修改」= 全量还原 draft 到已保存态，属破坏性操作（丢弃 N 处修改），执行前行内确认（见 §5.2 分层）。
- 测试三兄弟（测试消息/测试连接/匹配测试台）继续走已保存配置 + dirty 闸提示（现状约定，audit §5.7.5 资产，保留）。

## 3. 各分区职责边界（页面设计不得越界）

| 分区 | 职责（唯一） | 明确不放进来 | 数据面与新鲜度 |
|---|---|---|---|
| 监控台 | 现在的运行真相：状态、指标、来源/AI 健康、最近命中、日志 | 不放历史查询（>200 条去历史命中）、不放任何配置编辑（临时静音等也归设置，理由见 §5.5） | 内存环，事件推送，活页 |
| 去向 | 每条帖子的判定解释：14 类 outcome + detail，实时环 + 7 天 | 不放统计聚合（那是历史命中的画像职责）、不放规则编辑 | 实时环 10s 自刷（可暂停）+ 落盘静态 |
| 历史命中 | 全量命中记录与统计画像：查询、筛选、分页、趋势与榜单 | 不放实时数据（pc §6.2：不能把历史页做成"看似实时"，需带数据时间与 stale 态） | 落盘永久，手动刷新 |
| 日报 | 每日总结的阅读面：日期选择 + 日报正文 + 手动生成 | 不放命中明细（链接去历史命中） | 落盘，生成事件驱动刷新 |
| 设置 | 一切配置的唯一编辑面（draft-保存） | 不放运行状态监控（迷你状态除外）、诊断工具只读不编辑配置 | config.json 单源 |

跨页一致项（界面设计必须统一，audit §5.5 口径漂移的根治）：
- 来源显示名全应用一处映射（`sourceLabel` 口径），去向 / 历史命中 / 路由下拉三处共用；
- 命中行组件全应用一个（监控台与历史命中共用，含 👍/👎 与推送状态三态，静音 title 用通道化后的新文案）——audit §4.3 问题 6 文案漂移的根治是结构性的；
- 统计窗口口径必须在数字旁标注（「近 14 天」），列表筛选窗口独立标注（见 §5.1）。

## 4. 核心任务流走查（新分区下的验收标准）

**流 1 · 配置监控（首次上手，pc §4.1）**
启动 → 监控台（首启基线提示"现有帖子只记不推"）→ 侧栏「设置」，子导航默认落①监控内容 → 来源卡一键加预设 → 关键词卡填包含词（空=不推送的警示常显）→ 子导航点③推送通知 → 通道卡添加 Telegram、就绪点变绿 → 吸底保存栏 `Cmd+S`（距离 ≤ 一屏）→ `发送测试消息`（已保存，dirty 闸直通）→ 手机收到 → 切监控台等命中。
**走通保证**：组序 = 配置依赖序（先内容后通知）；保存栏吸底；测试操作与保存态解耦。

**流 2 · 看到命中 → 处置命中**
推送到手机，点链接直达原帖（不经界面）；或开应用在监控台「最近命中」读新行（300-400ms 一次性入场，dsn §6）——阅读中再到达的命中不推挤内容，顶部出「N 条新命中」角标，回顶才并入（§5.1 活列表规则）；👍/👎 反馈（aria-label 补齐，两页共用行组件）。
**走通保证**：阅读优先规则 + 行为入口内联。

**流 3 · 处置未收到推送（排障，可解释性主场景）**
监控台命中行推送状态 ✗ hover 见原因 → 侧栏紧邻「去向」→ 搜标题 → 看 outcome 与 detail → 按类别跳修复点：
- 凭据缺失/推送失败 → 设置③推送通知 → 通道卡；
- 未命中/置信度低 → 设置②智能匹配 或 ①监控内容；
- 来源过滤/排除词拦截 → 设置①监控内容 → 来源过滤 / 关键词；
- 挂起中 → 无需动作，等免打扰/摘要窗口结束（去向 detail 说明何时补发）。
**走通保证**：监控台→去向相邻（一跳）；outcome 类别 → 设置组的映射成立（六组按任务切分的直接收益）。

**流 4 · 回顾统计**
历史命中页：统计面板（标注「近 14 天固定窗口」）+ 列表（默认近 7 天，窗口差异行内标注，两数字不打架——audit 问题 #4 的解法）→ 筛选 + 分页（50/100/200 三档页大小 + 页码跳转）→ 零命中关键词旁「调整关键词」深链 → 设置①监控内容·关键词卡锚点定位 → 日报页回看当天总结（日期栏去掉 14 天截断，更早日期可展开——audit §4.2 问题 1）。
**走通保证**：口径标注规则 + 跨页锚点深链 + 筛选状态保持（quick-reference `state-preservation`）。

**流 5 · 调整规则（闭环）**
①改：设置①/②改关键词、阈值、规则 → ②验：子导航跳⑤数据与诊断 → 匹配测试台粘贴标题跑六阶段 trace（dirty 闸提示先保存）→ ③存：吸底保存 → ④察：`Cmd+1` 回监控台观察后续命中。
**走通保证**：测试台留在设置页内（与保存态耦合）但移出配置流中段；子导航两跳完成"改→验"；快捷键一跳回观察面。

## 5. 关键交互模式（全应用统一，页面设计直接引用）

### 5.1 长列表：分页 / 筛选 / 虚拟化策略

| 场景 | 策略 | 理由 |
|---|---|---|
| 历史命中（落盘，可达数千条） | **服务端分页为主**：页大小 50/100/200 三档（200 为 IPC 单次钳位上限，pc §6.4）+ 页码跳转 + 总页数 | 服务端分页把单次渲染量钉死在 ≤200；**放弃客户端虚拟化**——虚拟化与分页二选一，分页已解决数据量，而命中行高不定（语义命中带理由行、规则命中带规则名），虚拟化成本高收益为零 |
| 监控台最近命中 / 去向实时环（各 200 条内存） | **不虚拟化，控制更新方式**：增量插入 + 活列表规则 | React 19 下 200 行渲染可接受（audit §5.6）；真正的问题是阅读中断与整列表重排，不是行数 |
| 去向自动刷新 | **可暂停**：悬停、筛选激活、或用户手动点「暂停刷新」时停 10s 自刷；恢复手动 | dsn §2 telemetry 规则②（MASTER.md 落地页规则升级来的面板规范）：轮询类 UI 必须提供暂停/频率控制；audit 问题 #11 |
| 活列表规则（统一） | 用户视口不在列表顶部（或已交互）时，新数据不插入，顶部出「N 条新」角标，回顶/点击才并入；一次性 300-400ms 入场，禁循环动画 | 原则 5；范本 LogView（audit §5.7.2）推广到 HitList 与去向 |
| 日志（500 条环） | 加级别筛选 chips（info/warn/error）+ 保留现有跟随暂停 | audit §4.1 问题 3 |
| 设置卡内列表 | 废除 280px 嵌套滚动，自然高度 + 「展开全部 N 条」 | §2.3 配套修正 |
| 加载态 | **保留旧数据 + 局部 busy 指示**，禁止整屏替换为"正在加载"（audit 问题 #5：搜索防抖每 300ms 闪一次）；>1s 才考虑骨架（quick-reference `progressive-loading`） | 本地 IPC 快返回，旧数据保留比骨架更对 |
| 筛选状态 | 切分区返回后保留筛选与滚动位置 | quick-reference `state-preservation`（HIG/MD） |

虚拟化的明确决定：quick-reference `virtualize-lists`（50+ 项虚拟化）在本项目**仅适用于"单次全量渲染"的列表**；本骨架下所有大数据面都已被分页或 200 条环约束，因此全应用**不引入虚拟列表**。若未来历史命中提供"滚动聚合"视图再启用。

### 5.2 危险操作：三层确认模型

| 层 | 操作 | 确认方式 | 依据 |
|---|---|---|---|
| **draft 域内删除**（删规则/来源/通道/路由条目） | 未保存前均可还原 | **不弹确认**。删除即入"待删除"态（行内删除线视觉），保存栏状态区显示「含 N 项待删除」；「放弃修改」一键全还原。把现有 draft 兜底从"隐性"变"可见" | quick-reference `undo-support`（Apple HIG：破坏性操作允许撤销）——draft 本身就是 undo 通道；检索 A-3「确认对话框」针对 *irreversible* 动作，draft 删除未保存前可逆，弹窗是过度打断 |
| **立即不可逆** | 导入备份（覆盖全部配置，需重启）、放弃修改（丢 N 处 draft） | **确认对话框**：导入流程改为「先选文件 → 展示包内容摘要（含来源/通道/规则计数）→ 确认导入」（修 audit §4.5 问题 7 的顺序反常）；确认层内 danger 按钮与主操作视觉分离 | 检索 A-3（High：不可逆动作前必须确认）；quick-reference `destructive-emphasis`（HIG/MD：danger 色 + 与 primary 分离） |
| **破坏性导出** | 导出备份（**明文凭据**） | 确认层双重警告前置（pc §6.8 要求保留强警告位），成功提示再次提醒 | pc §6.8 |

### 5.3 未保存修改守卫

保留现有三件资产（audit §5.7.4：dirty-dot + leavebar 非路由拦截 + 测试 dirty 闸），补四条：
1. **saveMsg 生命周期**：dirty 即清除「已保存」文案（§2.4）——修 audit 问题 #7（文案矛盾导致用户误以为已保存）。
2. **`Cmd/Ctrl+S`** 全局保存。
3. **「放弃修改」常驻吸底保存栏**（现状只能被动等 leavebar，audit 问题 #2）。
4. **窗口隐藏不触发守卫**：关窗=最小化到托盘，组件不卸载、draft 留在内存，重开窗口原样恢复——这是"托盘常驻"产品身份的自然推论（pc §6.1）；守卫只在切分区（leavebar）与退出应用（若引入）时出现。依据：quick-reference `sheet-dismiss-confirm`（未保存变更离开前确认）只约束"真正离开"的场景。

### 5.4 操作反馈：行内三态，不建全局 toast

- **保留行内 `.feedback` 体系**（audit §5.3 评价"克制且合适"），统一三态：进行中（按钮 busy + 内容不替换）、成功（✓ + 时刻，简短）、失败（✗ + 原因 + 重试动作）。依据：检索 A-2（High：提交必须有 loading→success/error 反馈；Medium：成功需简短确认）；quick-reference `success-feedback` / `error-recovery`（错误必须带恢复路径）/ `error-clarity`。
- **放弃全局 toast**：桌面单窗口、操作都发生在具体卡片/保存栏上下文，行内反馈最贴近因果；toast 会造成第二套反馈体系（quick-reference `toast-accessibility` 的成本也就不必付）。
- **错误 ≠ 空**（原则 4）：所有数据面失败显示错误条 + 重试 + 旧数据保留，禁止 catch 后置空（audit §5.2 六个违规面的统一修法；History 统计面板为现成范本）。设置页 getConfig 失败给整页错误态 + 重试，不许永久 loading。
- 修复反馈生命周期漏洞：监控台 暂停/恢复/立即轮询 失败也要有失败反馈（现状 control() 无 catch，audit §5.3）。
- 反馈区域用 `aria-live` 或 `role="alert"`（现有 leavebar 已是范本）。

### 5.5 其他骨架级决定

- **临时静音（推送总开关）留在设置③推送策略，不挪监控台操作行**：监控台操作行承载"监控运行控制"（暂停/轮询/测试），静音是推送策略维度，混入会模糊两条控制轴。备选（监控台放快捷开关）留给界面设计阶段探索，默认不做。
- **可达性随骨架绑定**：侧栏 active 补 `aria-current`；Field label 全量补 `htmlFor` 关联（检索 A-2，High：label 必须带 for 属性——audit §5.4 发现全项目零调用）；筛选 chips 补 `aria-pressed`；投票按钮补 aria-label。
- **来源名 / 静音文案 / 命中行**统一单源（§3 跨页一致项）。
- **外链**保持主进程白名单受控跳转（pc §6.8），不新增跳转通道。
